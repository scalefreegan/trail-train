## What
Results capture and the archived race view. An "Archive with result" action on the active race (switcher menu) opens a picker over the Strava log to link the race activity; the server derives per-station splits by finding where the activity's GPS stream first passes within 150 m of each station's snapped `lat/lon` (stream via the existing `sync-streams.mjs` machinery), writes `result.json` per PRD §10 with `source: "track"`, and the review lets the user overwrite splits from official results (`source: "official"`) and add placement/notes. Sets `status: "archived"` and the pointer to null (generic mode). The race view of an archived race shows projected vs actual per station and the finish delta. Backfill MM100's `result.json` with its Strava activity and track splits.

## Why
The interview chose Strava activity + manual splits; the coach's `history[]` and the model check both benefit from actuals.

## Acceptance Criteria
- `scripts/race-result.mjs` `splitsFromStream(stream, stations)` pure function with `node --test` coverage including a station never approached (split `null`) and an out-and-back that passes a station twice (first pass wins unless `visit: 2` is set on the station).
- MM100 archived folder has `result.json` with `strava_activity_id`, `finish_h: 33.27`, track-derived splits, and the run in the log is labeled `race`.
- Archived race view: `RacePlanner` station table gains an "actual" column when `result.json` exists; `ModelCheck` shows the finish vs projected band.
- Archiving is refused if the linked activity's date is not within ±1 day of `race.date` in race-local time.

## Technical Context
- Streams fetch/cache: `scripts/sync-streams.mjs` (`FETCH_CAP`, window constants); Strava MCP tools also available for manual verification.
- Station coordinates: `build/course.json` `aid_stations[].lat/lon`.

## Constraints
- Do not re-fetch streams for every activity; only the linked one.

## Out of Scope
Scraping official results; DNF analytics.
