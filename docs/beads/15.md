## What
Re-intake with merge. "Refresh from sources" on an existing race re-runs stages 1-3 into a shadow folder `races/<slug>/.refresh/`, then computes a field-level diff against the current files: fields with `provenance.by: "user"` are kept (agent value shown as a suggestion), `agent`/`matcher`/`computed` fields are updated, arrays (aid stations, targets) are diffed by key (`name`, `wk`). The review screen shows the diff (old → new per field, grouped by file) and only on Accept are the files rewritten; Reject deletes the shadow folder. `sources/` gains a dated manifest so the previous manual is kept.

## Why
The 2027 Softie manual and GPX will drop months after the first intake; hand edits (cutoffs, crew notes) must survive.

## Acceptance Criteria
- Pure merge function `scripts/race-merge.mjs` `mergeRace(current, incoming)` → `{merged, diff[], conflicts[]}` with `node --test` coverage: user field preserved, agent field updated, aid station added/removed/renamed, target row changed.
- Nothing under `races/<slug>/` except `.refresh/` and `sources/` changes before Accept.
- Active race stays active during and after refresh; `plan.json` and `result.json` are never touched by merge.
- Re-running intake on the archived MM100 folder against its cached sources yields an empty diff (regression test of the pipeline's determinism, allowing provenance timestamps to differ).

## Technical Context
- Stage endpoints from the intake beads accept `{refresh: true}`; the dialog bead's review component is reused with a diff mode.

## Constraints
- Deterministic merge; no agent involvement in merging.

## Out of Scope
Three-way merge with git; versioned history beyond the sources manifest.
