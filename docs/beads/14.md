## What
The New Race dialog and the review/activate flow in the web client. "New race…" from the switcher opens a modal: site URL, extra URLs, PDF/GPX uploads, edition year, free-text "what matters to me", theme preset picker. It runs stages 1→2→3 with streamed progress (reusing the resync status UI), then shows a review screen: editable aid-station table (name, mile, cutoff, access flags), elevation profile preview from `build/course.json`, block targets table (editable), nutrition summary, theme preview swatch, and an `unresolved[]` list that must be empty or acknowledged before Activate. Edits write back with `provenance.by: "user"`. Activate sets `status: "active"`, writes the pointer in train mode, and archives nothing. "Save draft" keeps it selectable from the switcher's drafts group.

## Why
The interview chose an in-app dialog from day one and a draft → review → activate gate.

## Acceptance Criteria
- Dialog and review live in `web/src/race/RaceIntake.tsx`; opened from `CommandBar`'s menu; escape/close never loses a completed draft (it is on disk).
- `PUT /api/races/:slug` validated write of the editable subset; refuses fields the review screen does not expose.
- Activate is disabled while `status` is not `draft` or `unresolved` is non-empty and unacknowledged; success reloads snapshots.
- End-to-end manual run recorded in the closing note: San Juan Softie 2027 draft created, reviewed, activated, switcher shows it, race view renders.
- `npm run build` passes.

## Technical Context
- Card/modal patterns: `web/src/race/CrewSheet.tsx` (modal with `onClose`), `web/src/CoachSettings.tsx` (settings dialog with validated PUT).
- Progress streaming: resync status in `CommandBar`.

## Constraints
- No new UI dependencies; Motion is already present for transitions.

## Out of Scope
Re-intake diff view, theme application, results.
